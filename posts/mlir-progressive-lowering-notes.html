MLIR: Lowering Code Without Losing the Plot

May 30, 2026 • 5 min read

1. Why MLIR Exists

LLVM IR works very well for low-level optimization, but by the time code reaches it, many source-level details are already gone. For modern workloads, especially ML and hardware-specific compilation, we often need optimizations at several abstraction levels instead of one final IR.

2. The Core Idea

MLIR is built around progressive lowering: move from source-level concepts to machine-level code through multiple intermediate representations. A PyTorch program, for example, can move through Torch, Linalg, Affine, and LLVM dialects before becoming machine code.

3. Dialects as Layers

A dialect captures one level of meaning. Higher dialects can preserve tensors, shapes, and domain operations, while lower dialects expose loops, memory, and hardware details. This makes the compiler pipeline flexible instead of forcing every frontend into one fixed IR too early.

4. SSA Refresher

MLIR uses SSA, where each value is assigned once. This makes dependencies clear and helps optimizations like constant propagation, dead code elimination, and data-flow analysis. Branches merge values using phi-like semantics, so the chosen value depends on the control-flow path.

5. The Four Building Blocks

  • Operation: the basic executable unit, with inputs, outputs, attributes, and optional nested regions.
  • Region: a container owned by an operation. This is one of MLIR's key differences from LLVM IR.
  • Block: a sequence of operations, similar to a compiler basic block.
  • Value: an SSA value produced by operations or passed as a block argument.

6. Mental Model

An MLIR operation can take values as inputs, produce values as outputs, carry attributes as metadata, and own regions. Those regions contain blocks, and blocks contain more operations. This recursive structure lets MLIR represent both low-level instructions and high-level program structure in one infrastructure.
